# S4: SQLite read path (bbox query, WKB decode, triangulation per tile)

Status: done 2026-11-13 on the workstation (4 CPUs via `taskset`). Pass for
polygon tiles up to level 3; level 4 is marginal (see "Implications").

## Setup

- Stores: the synthetic `full` store (6.0M objects, 1.65 GB) in spatial
  (Morton) object order, and the same objects in random order (`fullrand`).
  Layer: `cells` (1M polygons, 8 to 32 vertices).
- Code: `server/src/compass_studio/annot/store.py` (read-only store, schema
  check, R-tree query, WKB decode, Arrow polygon tile) and
  `annot/triangulate.py` (earcut). Harness: `spikes/S4/bench.py`.
- Tiles: 512 px at level l, i.e. 512 x 2^l level-0 px. 200 tiles per case,
  placed either uniformly over the image grid (includes empty tiles) or on
  tissue (a tile containing a random object of the layer).
- Each tile: R-tree query joined with objects and groups, WKB decode (direct
  parser and shapely, both timed), earcut, Arrow IPC encode. Then whole tiles
  on 1 and 4 threads, one SQLite connection per thread.
- Python 3.13, SQLite 3.45 (bundled), shapely 2.2, mapbox-earcut 2.1.

## Results (single thread, on-tissue tiles, p95)

| Level (tile px) | Objects p50 / p95 | Spatial order | Random order | Tile size p95 |
|---|---|---|---|---|
| 0 (512) | 15 / 25 | 0.3 ms | 0.4 ms | 11 kB |
| 1 (1,024) | 57 / 94 | 0.8 ms | 1.1 ms | 36 kB |
| 2 (2,048) | 215 / 339 | 2.7 ms | 3.7 ms | 132 kB |
| 3 (4,096) | 847 / 1,307 | 10 ms | 15 ms | 0.5 MB |
| 4 (8,192) | 3,493 / 5,163 | 40 ms | 63 ms | 2.0 MB |

Stage split at level 4, spatial order (p95): query 18 ms, decode 7 ms
(direct) or 4 ms (shapely), earcut 14 ms, Arrow encode 0.4 ms.

- A fresh connection (empty SQLite page cache) costs about the same in
  spatial order and 1.5 to 2x in random order. The OS page cache was warm
  (the store fits in RAM); a cold OS cache was not tested (needs root).
- Object order matters: random order doubles the query time at levels 3 and
  4 (poorer page locality). The viewer cannot change COMPASS stores, so real
  stores will sit somewhere between these two.
- Shapely decodes faster than the direct Python parser from level 2 up; the
  direct parser wins only on tiny tiles. Use shapely.
- **Threads do not help**: 4 threads give the same throughput as 1 in spatial
  order (38 tiles/s at level 4) and up to 1.7x in random order, with latency
  growing about 4x. The per-polygon Python loops (earcut calls, ring
  handling) hold the GIL; only the SQLite part runs in parallel.
- Exporting the whole 5M point layer from SQLite takes 5.7 s (5M Python
  tuples through a join and GROUP BY), in either order.

## Implications

- Polygon tiles up to level 3 fit easily within the 100 ms tile-to-screen
  budget (server under 15 ms p95). At level 4 the server alone takes 40 to
  63 ms p95 and the tile is 2 MB. This supports D6's level of detail: serve
  triangulated polygons up to level 3 and switch to centroids or a density
  raster beyond (proposed threshold; to confirm when the viewer is built).
- Concurrency needs work before many tiles are requested at once: a process
  pool, or batching earcut over a whole tile in one native call, or caching
  triangles (a derived, read-only cache next to the store).
- Point layers should be cached after the first export (for example as an
  Arrow file in the disk cache, keyed by store and layer), or read with a
  leaner query: 5.7 s is too slow to repeat every time a layer is opened.

## Not tested

- Real COMPASS stores at scale (only the 14-object sample exists).
- Cold OS page cache; slow disks.
- Polygons with holes at scale (tested for correctness only).
- Line and circle objects.
