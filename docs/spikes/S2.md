# S2: deck.gl OrthographicView and TileLayer

Status: passed 2026-11-13 (owner's call: performance is adequate for
day-to-day work). Rendering and precision pass on the reference laptop.
Follow-ups for milestone 3: stutter when panning fast (manual), and cold
tile-to-screen p95 slightly over budget in Firefox (see "Reference laptop").

## Setup

- Server: `compass-studio-serve` (FastAPI), tiles read with the direct shard
  reader, JPEG q90 via Pillow, 4 CPUs (`taskset -c 0-3`), address space capped
  at 32 GB.
- Client: deck.gl 9.4.1, OrthographicView (`flipY`), TileLayer (512 px tiles,
  `best-available`, 12 concurrent requests) with BitmapLayer sub-layers.
- Images: the sample COMPASS slide (52,592 x 110,886 px, 8 levels) and a
  procedural 200,000 x 200,000 px pyramid (10 levels).
- Browser: Firefox 158, headless, 1366 x 682 viewport (the `--window-size`
  flag was ignored), DPR 1. Workstation GPU: NVIDIA (Firefox reports a
  sanitised renderer string, "GeForce GTX 980, or similar").

## Precision (`bench=jitter`)

A white shape's left edge at level-0 x0 in {1,000, 50,000, 100,000, 150,000,
199,000, 262,000} + 0.3 px, zoom 0 to 8 (up to 256x overzoom), view target
moved in 1/16 px steps; the edge column is read back and compared with the
exact position. Antialiasing off.

| Variant | Max error (device px) |
|---|---|
| SolidPolygonLayer, accessor data, absolute coords | 0 |
| BitmapLayer, absolute bounds | 0 |
| SolidPolygonLayer, binary Float32Array, absolute coords | 1 (zoom 8 only) |
| Same, relative coords + `modelMatrix` translation | 1 (zoom 8 only) |

- No motion jitter in any variant: the error is constant across sub-pixel
  pan steps. deck.gl's offset mode subtracts the camera position in 64-bit JS
  and keeps fp64 positions for accessor-built layers.
- Float32 positions give a static offset of at most half an ulp times the
  zoom factor: at 131k to 262k px, 1/128 px x 2^zoom (0.06 px at 8x, 2 px
  worst case at 256x). Acceptable for annotation buffers (D6).
- `modelMatrix` does not recover precision (the matrix is float32 in the
  shader). `coordinateOrigin` is ignored for CARTESIAN coordinates in an
  OrthographicView (shapes rendered off-screen), so it is not a tool here.

## Pan and zoom (`bench=pan`)

Scripted flight over the tissue bounding box: zoom in from fit to 1:1
(3 s), pans at 1,500 screen px/s at zoom 0, -2, -4 and +2, zoom out (3 s).
Three runs: cold (new tile URLs), http (fresh layer, same URLs), resident
(tiles already in deck's cache).

| | Sample slide | Synthetic 200k |
|---|---|---|
| Frame interval p95 / p99, all phases | 17.1 / 17.4 ms | 17.1 / 17.5 ms |
| Frames over 17.5 ms | under 1.1 % | under 1.1 % |
| Render CPU per frame, p95 / max | 2 / 5 ms | 2 / 4 ms |
| Tiles, cold run | 380 | 571 (13 aborted) |
| Request to screen, cold, p50 / p95 / max | 23 / 65 / 131 ms | 24 / 59 / 143 ms |
| Server read p95 / encode p95 | 2.6 / 2.5 ms | 4.9 / 3.8 ms |

- Headless Firefox ticks frames on a fixed ~17.06 ms timer, so these frame
  intervals only show the renderer never fell behind; they say nothing about
  vsync on real hardware. Firefox also rounds `performance.now()` to 1 ms.
- Cold tile-to-screen p95 is within the 100 ms budget; most of it is queueing
  and client-side decode, not the server (about 5 ms p95 read plus encode).
- The "http" run's latencies are close to the cold run's: whether the browser
  HTTP cache served those tiles was not verified (responses carry
  `Authorization`-gated `Cache-Control: private`). Check transfer sizes on
  the laptop before relying on it.
- One long frame (122 ms) at the start of a cold zoom-in on the synthetic
  pyramid, not repeated; likely first texture uploads. Watch for it on the
  laptop.

## Reference laptop (2026-11-13)

Firefox 160 and Brave (Chromium 157), headed, DPR 1; viewports 1731 x 1228
(Firefox) and 2043 x 915 (Brave). AMD integrated GPU (Firefox reports the
bucketed string "Radeon R9 200 Series, or similar"; Brave masks it). Server
on the same laptop, not CPU-limited.

**Precision**: identical to the workstation. Absolute-coordinate variants:
0 px error everywhere, in both browsers. Float32 binary variants: at most
1 px, at x0 = 50,000.3 only; at zoom 0 and 2 it flips between 0 and 1 px
across pan steps (an edge sitting near a pixel centre), static otherwise.
D5's precision item is closed.

**Scripted pan/zoom** (frame intervals now vsync-paced):

| | Brave, sample | Brave, 200k | Firefox, sample | Firefox, 200k |
|---|---|---|---|---|
| Frame p95, pan phases | 16.8 ms | 16.8 ms | 17.2 ms | 17.2 ms |
| Frame p95, worst zoom phase | 16.8 ms | 16.8 ms | 33.1 ms | 33.1 ms |
| Frames over 17.5 ms, worst phase | 1.1 % | 0.6 % | 6 % | 5.9 % |
| Longest frame | 83 ms | 33 ms | 67 ms | 34 ms |
| Render CPU p95 | under 4 ms | under 4 ms | under 4 ms | under 4 ms |
| Cold request to screen, p50 / p95 | 42 / 90 ms | 42 / 92 ms | 57 / 110 ms | 57 / 106 ms |
| HTTP-cached request to screen, p95 | 62 ms | 58 ms | 85 ms | 79 ms |
| Server read + encode, p95 each | 4.4 / 6.8 ms | 11.6 / 10.0 ms | 3.7 / 6.5 ms | 10.3 / 8.4 ms |

- Brave holds 60 fps through every scripted phase. Firefox holds it while
  panning and drops frames (to 30 fps steps) during zoom phases, when many
  tiles arrive and are uploaded at once. Render CPU stays under 4 ms at p95,
  so the drops are outside deck's JS (texture upload, decode, compositing).
- Manual use (owner): over 52 fps throughout, with visible stutter when
  panning fast. The scripted pans run at 1,500 screen px/s, slower than a
  fast manual fling, so the bench does not yet reproduce it.
- Cold tile-to-screen p95: Brave within the 100 ms budget, Firefox 6 to 10 %
  over. Server time is about 10 to 20 ms of that; the rest is client-side
  queueing and decode. The synthetic image's server cost includes drawing
  the test pattern, so it is not representative of real tiles.
- The HTTP cache does help (http run p95 15 to 35 ms lower than cold).

**Follow-ups for milestone 3** (not decided here):

- Add a fast-fling phase (for example 5,000 px/s) to `bench=pan` to reproduce
  the stutter and measure fixes against it.
- Candidate causes and fixes to test: the browser's 6-connection limit per
  host on HTTP/1.1 (TileLayer asks for 12 at a time; HTTP/2 or a batched
  tile endpoint would lift it); too many texture uploads in one frame
  (spread uploads over frames); request churn while flinging (`debounceTime`,
  prefetching a ring of tiles around the viewport); ImageBitmap decode cost
  in Firefox.

## Running on the laptop

    cd server && uv sync
    cd ../web && pnpm install && pnpm build
    cd ../server && uv run compass-studio-serve --image sample=<path to .zarr> \
        --synthetic synth200k=200000x200000 --web ../web/dist \
        --spike-results ../spikes/S2/results

Open the printed URL in a normal (headed) browser window, adding
`bench.html?image=sample&bench=pan`, `bench.html?image=synth200k&bench=pan`
or `bench.html?bench=jitter` before the `#token=...` fragment. Results land
in `spikes/S2/results/`. Without `bench`, `bench.html` is an interactive
viewer with an fps HUD. (Since milestone 3 the benches live in `bench.html`;
`/` is the application.)

Workstation, 4 server CPUs, headless Firefox 158, sample slide, the pan
flight plus two fling legs (6,000 screen px/s at levels 0 and 1), each
variant twice, cold and from the HTTP cache. `bench.html?bench=pan&tiles=<preset>`.
Sharp = per frame, share of on-screen tiles loaded at the target level.

| Preset | Change from S2 | Sharp, pans and flings | Sharp, zoom out | Requests | Tile to screen p95 |
|---|---|---|---|---|---|
| s2 | (12 requests) | 0.94 to 0.99 | 0.86 | 458 | 52 to 65 ms |
| req6 | 6 requests | 0.94 to 0.99 | 0.86 | 456 | 32 to 42 ms |
| ring1 | prefetch ring 1 | 0.98 to 1.0 | 0.92 | 880 | 56 to 62 ms |
| gate2 | 2 texture uploads per frame | 0.86 to 0.98 | 0.64 | 453 | 33 to 37 ms |

Frame intervals had p99 of about 17 ms in every variant and deck render time
at most 8 ms: the fast-pan stutter seen on the laptop does not reproduce
on the workstation, so it can't be attributed here; headless Firefox ticks
on a fixed timer, so these numbers are a ceiling check only. Tile requests
in the default roughly double, which the server handles (S1: about 1,100
tiles/s).
