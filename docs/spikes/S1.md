# S1: tile throughput from the sharded directory store

Status: done 2026-11-13 on the workstation. Pass: no throughput collapse up
to 64 concurrent requests; server p95 per tile 3 to 6 ms.

## Setup

- Image: the sample COMPASS slide (52,592 x 110,886 px, 8 levels, 4096 px
  shards of 512 px chunks, Blosc zstd + bitshuffle). OS page cache warm (the
  2.1 GB store fits in RAM); a cold cache was not tested (needs root).
- Tiles: 1,802 sampled with `spikes/S1/bench.py tiles`: 1,402 tissue tiles
  over levels 0 to 4, weighted towards level 0 (as when viewing), plus 400
  background tiles (empty chunks or missing shards).
- Readers: the direct shard reader (`imaging/shards.py`, one `pread` per
  tile, cached shard indexes) and zarr-python 3.4.2 (`--reader zarr`).
- Server: `compass-studio-serve`, one uvicorn worker, pinned to 4 CPUs.
  Load generator on 4 other CPUs, httpx, 4 client processes.

## Results

**Read + decode in process** (4 CPUs, tiles/s; latency p95):

| Threads | Direct reader | zarr-python |
|---|---|---|
| 1 | 977 (1.6 ms) | 1,090 (1.2 ms) |
| 4 | 4,826 (1.5 ms) | 1,636 (3.9 ms) |
| 16 | 4,188 (9.9 ms) | 1,441 (15.5 ms) |
| 64 | 3,907 (29.7 ms) | 1,497 (54.2 ms) |

zarr-python stops scaling at 2 threads; the direct reader scales with the
CPUs and is about 3x faster at 4 or more threads.

**Encoders** (Pillow 13, 150 tissue tiles, 768 kB raw each):

| Encoder | p50 / p95 | Size p50 |
|---|---|---|
| JPEG q80 | 0.48 / 0.60 ms | 65 kB |
| JPEG q90 | 0.54 / 0.70 ms | 93 kB |
| PNG level 1 | 13.7 / 17.5 ms | 457 kB |
| PNG level 6 | 25.9 / 42.9 ms | 415 kB |
| WebP lossless, method 0 | 5.8 / 6.3 ms | 424 kB |
| WebP lossless, method 4 | 67.8 / 92.7 ms | 339 kB |

**End to end over HTTP**, JPEG q90 (tiles/s; latency p95):

| Concurrent | Direct reader, tile pool | Direct reader, Starlette pool | zarr-python, tile pool |
|---|---|---|---|
| 1 | 361 (3.9 ms) | 366 (3.9 ms) | 375 (3.5 ms) |
| 8 | 1,038 (10.3 ms) | 955 (12.4 ms) | 724 (14.4 ms) |
| 32 | 1,117 (34.4 ms) | 936 (43.0 ms) | 714 (49.2 ms) |
| 64 | 1,102 (68.9 ms) | 908 (82.7 ms) | 708 (95.5 ms) |

Server-side read and encode p95 with the direct reader and tile pool: 2.9 and
2.7 ms at any concurrency. Lossless WebP over HTTP: 497 tiles/s at 8
concurrent requests (p95 22 ms), 507 at 64.

- No collapse in any variant. Throughput plateaus once the 4 server CPUs are
  busy; latency then grows linearly with queue depth.
- The direct reader gives about 50 % more end-to-end throughput than
  zarr-python and halves the server read time under load. Per-request HTTP
  overhead in Python (about 3.5 ms of CPU) now dominates, not the image read.
- A dedicated tile thread pool (one thread per CPU) beats Starlette's
  default 40-thread pool by about 15 % and keeps server times flat.
- A browser on HTTP/1.1 opens at most 6 connections per host, so one viewer
  sits at about 8 concurrent requests: p95 about 10 ms server round trip,
  well inside the 100 ms tile-to-screen budget.
- A first run with a single-process load generator appeared to show a
  collapse above 16 concurrent requests (to 312 tiles/s, p95 600 ms); that
  was the client (one Python event loop running httpx), not the server.

## Implications

- D3: use the direct shard reader, with zarr-python as the fallback for
  layouts and codecs it does not handle (already implemented).
- D4: lossless tiles as WebP lossless, method 0 (faster than PNG level 1 and
  smaller). JPEG q90 encoding costs about 0.5 ms and a tile read about
  1.5 ms, so a disk cache for transcoded JPEG tiles is unlikely to pay off
  on a local SSD; revisit only for slow storage (network mounts).

## Not tested

- Cold OS page cache, spinning disks, network file systems.
- Multichannel (non-RGB) tiles.
- Several uvicorn worker processes.
- HTTP/2.
